# メモリの基礎（脆弱性を読むために）

作成日: 2026-10-23

CVEの記録に出てくる、メモリまわりの用語や考え方の土台をまとめる。ヒープのはみ出しの詳しい話は [CWE-122_ヒープベースのバッファオーバーフロー.md](CWE-122_ヒープベースのバッファオーバーフロー.md) にある。

---

## なぜメモリの知識がいるのか

- **深刻な脆弱性の多くは、メモリの扱いの誤り**。Chromium は、2015年以降の深刻度 High・Critical のバグ912件を調べ、約70%がメモリ安全性の問題で、その半分が use-after-free だったとしている。Microsoft も、毎年CVEを割り当てる脆弱性の約70%がメモリ安全性の問題だとしている（2019年）。
- PHP・Java・JavaScriptのコードではまず起きないが、**それらを動かす処理系（PHP本体、JVM、V8、各種ライブラリ）は C・C++ で書かれている**。今回の記録の PHP本体の脆弱性は、ほぼすべてこの部分の問題。

---

## 1. メモリとアドレス

- メモリは、**1バイトずつ番号が振られた巨大な配列**のようなもの。この番号を**アドレス**と呼び、ふつうは16進数で書く（例: `0x7ffd3a2c1e40`）。
- 64ビットのプログラムでは、アドレスは8バイト（64ビット）。
- **ポインタ**は、アドレスを入れておく変数。「データそのもの」ではなく「データがどこにあるか」を持つ。
  - C では、ポインタに数を足し引きして、メモリ上を自由に動ける。範囲を確かめる仕組みはない。これがメモリの脆弱性の根っこ。

---

## 2. 仮想メモリとプロセス

- 各プロセス（実行中のプログラム）は、**自分専用のアドレス空間（仮想メモリ）**を持つ。OSが、それを実際のメモリ（RAM）に対応づけている。
- 対応づけは **4KB のページ**単位。ページごとに「読める」「書ける」「実行できる」の許可が付いている。
- **別のプロセスのメモリは、ふつうは直接見えない**。そのため、メモリの脆弱性の影響は、基本的に**そのプロセスの中身と権限**に限られる。
  - 記録によく出てくる「Webワーカーの権限でコードを実行される」は、このこと（[CVE-2026-109618](../PHP/2026/10/21/CVE-2026-109618.md)）。
- 対応づけのない場所や、許可のない操作（書けないページへの書き込みなど）をすると、OSがプロセスを止める。
  - Linux では `SIGSEGV`（Segmentation fault）、Windows では「アクセス違反」（例外コード `0xC0000005`）。
  - 記録でいう「クラッシュ（DoS）」の多くはこれ（[CVE-2026-91765](../PHP/2026/09/24/CVE-2026-91765.md) など）。

---

## 3. プロセスのメモリの中身

典型的なイメージ（実際の配置はOSや、後述のASLRで変わる）:

```text
高いアドレス
┌──────────────────────┐
│ スタック             │ ↓ 関数を呼ぶたびに下へ伸びる
│                      │
│ （空き）             │
│                      │
│ 共有ライブラリ、     │
│ mmap で確保した領域  │
│                      │
│ ヒープ               │ ↑ 確保するたびに上へ伸びる
├──────────────────────┤
│ データ               │ グローバル変数、定数
├──────────────────────┤
│ コード               │ プログラムの命令
└──────────────────────┘
低いアドレス
```

| 領域 | 中身 | 許可 | 関係する脆弱性 |
|---|---|---|---|
| コード | プログラムの命令 | 読む・実行 | 書き換えられない。攻撃者は、既存の命令の断片を使い回すことがある |
| データ | グローバル変数、定数 | 読む（・書く） | — |
| ヒープ | 実行中に確保するデータ | 読む・書く | ヒープのはみ出し（CWE-122）、use-after-free（CWE-416） |
| スタック | 関数のローカル変数、引数、戻り先 | 読む・書く | スタックのはみ出し（CWE-121）、深い再帰による使い切り（CWE-674） |

## 4. スタック

関数を呼ぶたびに、その関数用の区画（**フレーム**）を積み、関数から戻ると取り除く。

```text
フレーム（1回の関数呼び出しぶん）
┌────────────────────────┐
│ ローカル変数（配列など） │ ← ここからはみ出すと…
├────────────────────────┤
│ 戻り先のアドレス         │ ← ここを書き換えられる
├────────────────────────┤
│ 呼び出し元のフレーム     │
└────────────────────────┘
```

- **ローカル変数のすぐ近くに「関数が終わったら戻る場所」が置かれる**。ローカルの配列からはみ出して書き込めると、戻り先を書き換え、関数から戻るときに攻撃者の決めた場所へ飛ばせる。これが古典的な**スタックベースのバッファオーバーフロー**（CWE-121）。
- スタックの大きさには上限がある（OSの既定で1〜8MB程度）。**再帰が深すぎると使い切って**、プロセスが落ちる（CWE-674、制御されない再帰）。
  - 記録の例: [CVE-2026-91765](../PHP/2026/09/24/CVE-2026-91765.md)（SOAP、5万段のネスト）、[CVE-2026-109449](../PHP/2026/10/15/CVE-2026-109449.md)（Symfony ExpressionLanguage）、[CVE-2026-109413](../PHP/2026/10/15/CVE-2026-109413.md)（Symfony Yaml）。
  - 修正は、どれも「ネストの上限を設ける」か「再帰をループに書き換える」。

### 「スタックオーバーフロー」は2つの意味で使われる

| 意味 | 中身 | 主な影響 |
|---|---|---|
| スタックの使い切り（stack exhaustion） | 再帰などで、スタックの上限を超える | クラッシュ（DoS） |
| スタック上のバッファのはみ出し（CWE-121） | ローカルの配列の範囲を超えて書く | メモリ破壊、コード実行 |

どちらの意味かで深刻さがまったく違うので、文脈で見分ける。

---

## 5. ヒープ

実行してみるまで大きさが決まらないデータを置く場所。C では `malloc()` で確保し、`free()` で解放する。空き領域の管理は**アロケータ**（`malloc()` の実装や、PHPの ZendMM）が受け持つ。

```text
確保する → 使う → 解放する → （解放後は、二度と触らない）
```

この流れのどこかを間違えると、脆弱性になる。

| 間違い | CWE | 起きること | 記録の例 |
|---|---|---|---|
| 確保した大きさを超えて読み書きする | CWE-122、125、787 | 情報漏えい、メモリ破壊 | [CWE-122の解説](CWE-122_ヒープベースのバッファオーバーフロー.md) を参照 |
| 解放した後に使う（use-after-free） | CWE-416 | その場所に入った別のデータを読み書きしてしまう | PHP2Shell（[109618](../PHP/2026/10/21/CVE-2026-109618.md)、[109619](../PHP/2026/10/21/CVE-2026-109619.md)） |
| 同じ場所を2回解放する（double free） | CWE-415 | アロケータの管理情報が壊れる | — |
| 解放し忘れる（メモリリーク） | CWE-401 | メモリが少しずつ減り、いずれ足りなくなる（DoS） | — |

### 初期化されていないメモリ

確保した直後のメモリには、**前に使っていたデータの残りかす**が入っている。初期化を忘れると、その中身が漏れたり、実行するたびに動きが変わったりする。

- PHPの GHSA-ch8v-r6jh-4vvr（`FILTER_SANITIZE_ENCODED`、CVE番号なし、2026-09-24 に修正）: 256要素の表のうち、最後の1つだけ初期化していなかった。0xFF をエンコードするかどうかが、スタックの残りかすで決まっていた。
- [CVE-2026-109618](../PHP/2026/10/21/CVE-2026-109618.md): 初期化し終わる前のリクエスト用のメモリが、終了処理から参照される（CWE-824、未初期化ポインタへのアクセス）。

## 6. メモリ安全性の2つの軸

メモリの脆弱性は、大きく「場所を間違える」か「時期を間違える」かに分けられる。

| 軸 | 間違い | 代表的なCWE |
|---|---|---|
| **空間（どこに触るか）** | 確保した範囲の外に触る | CWE-121、122、125、787 |
| **時間（いつ触るか）** | 確保する前、解放した後に触る | CWE-416（use-after-free）、415（double free）、824（未初期化ポインタ） |

ほかに、初期化を忘れる、型を取り違える（CWE-843）などもある。

## 7. 整数とメモリ

C の整数は、型ごとにバイト数が決まっていて、**表せる範囲を超えるとあふれる**。

| 型 | 大きさ | 範囲 | あふれたとき |
|---|---|---|---|
| `int`（符号付き） | 4バイト | 約 -21億 〜 +21億 | **未定義動作**。何が起きてもよいことになっていて、コンパイラは「起きない」前提で最適化する |
| `unsigned int`（符号なし） | 4バイト | 0 〜 約43億 | 0 に戻って数え直す（定義された動き） |
| `size_t`（大きさ用、符号なし） | 8バイト（64ビット） | 0 〜 約1800京 | 同上。`0 - 1` は最大値になる |

- **大きさの計算があふれると、小さな区画しか確保されず、はみ出しにつながる**（[CWE-122の解説](CWE-122_ヒープベースのバッファオーバーフロー.md) の「よくある原因」）。
- [CVE-2025-14181](../PHP/2026/09/24/CVE-2025-14181.md): あふれを確かめる処理が、符号付き整数のオーバーフロー（未定義動作）に頼っていたため、コンパイラに消された。
- [CVE-2026-91767](../PHP/2026/09/24/CVE-2026-91767.md): `size_t` の引き算がマイナスにならず、巨大な値に化けた。

### PHPの整数との違い

- PHPの `int` は符号付きで、64ビット環境なら最大値は約 9×10^18（`PHP_INT_MAX`）。符号なしの整数はない。
- 範囲を超えると、**あふれずに float（浮動小数点数）に変わる**（`PHP_INT_MAX + 1` は `float(9.2233720368548E+18)`）。C のように黙って小さな値に化けることはない。

## 8. 文字列の持ち方

| | C の文字列 | PHP の文字列（`zend_string`） |
|---|---|---|
| 終わりの目印 | **NUL（0x00）で終わる**。長さは持たず、NULまで数える（`strlen()`） | **長さ（`len`）を別に持つ** |
| NULを含められるか | できない（そこで終わりと見なされる） | できる（`"foo\0bar"` は長さ7） |
| 末尾のNUL | 必須 | C の関数にそのまま渡せるよう、末尾にもNULを置いている |

**2つの世界の境目で、長さの食い違いが起きやすい**。

- [CVE-2026-92842](../PHP/2026/09/24/CVE-2026-92842.md): NULで止まる関数でコピーしたので区画は短くなったのに、長さは PHP 側の値を使い続けた。
- [CVE-2026-105482](../Node.js/2026/10/21/CVE-2026-105482.md)（Node.js）: NULを含むホスト名が、C の名前解決に渡るときにNULで切り詰められた。
- [CVE-2026-17545](../PHP/2026/09/24/CVE-2026-17545.md) もパスの文字列を OS に渡すところの問題で、境目の確認漏れという点で似ている。

## 9. 言語ごとのメモリ管理

| 言語 | 解放するのは誰か | 範囲の確認 | メモリの脆弱性 |
|---|---|---|---|
| C・C++ | **プログラマー**（`free()`、`delete`） | なし | 起きる |
| PHP | 参照カウント（使う人が0になったら解放）＋循環参照を回収するGC | あり | PHPのコードでは起きない（FFI拡張で生のメモリを扱う場合は別） |
| Java・JavaScript | ガベージコレクタ（GC） | あり | コードでは起きない |
| Rust | コンパイラが所有権のルールで確かめる | あり | `unsafe` の部分を除いて起きない |

- 安全な言語でも、**処理系やライブラリは C・C++ で書かれている**。PHP本体、Javaの HotSpot、JavaScriptの V8、Node.js が使う Brotli（[CVE-2026-111497](../Node.js/2026/10/21/CVE-2026-111497.md)）など。
- そのため、**アプリのコードがどれだけ正しくても、処理系の脆弱性は更新でしか直せない**。

## 10. PHPのメモリ

- PHPは、独自のメモリ管理（**ZendMM**）でヒープを管理している。2MBの塊を4KBのページに分け、小さな確保は同じ大きさの区画を並べた「ビン」から渡す（詳しくは [CWE-122の解説](CWE-122_ヒープベースのバッファオーバーフロー.md) の「PHPの場合」）。
- ZendMM で確保したメモリは、すべて **`memory_limit`** に数えられる。超えると、Laravelでもおなじみの「Allowed memory size of ... bytes exhausted」の致命的エラーになる。
  - このとき、PHPは処理の途中から一気に抜け出す（bailout）。その抜け出し方に問題があったのが [CVE-2026-109618](../PHP/2026/10/21/CVE-2026-109618.md)。
- **リクエスト用のメモリは、リクエストが終わると片付けられる**。一方で、mod_php や PHP-FPM はプロセス（ワーカー）を使い回すので、プロセスのグローバルな状態は次のリクエストに持ち越される。
  - 片付けが中途半端だと、次のリクエストが前のリクエストの解放済みメモリに触れてしまう。これが [CVE-2026-109619](../PHP/2026/10/21/CVE-2026-109619.md)。
- 名前が `p` で始まる関数（`pemalloc()`、`pestrdup()` など）は、引数しだいで、リクエストをまたいで残る「持続的な」メモリを確保できる。

## 11. OS・コンパイラによる防御

どれも**被害を減らす・攻撃を難しくする**もので、脆弱性そのものを直すものではない。

| 仕組み | 何をするか | 主に防ぐもの | 限界 |
|---|---|---|---|
| **DEP / NX** | ヒープやスタックなど、データ用のページを実行できなくする | データとして書き込んだ命令の実行 | 既存の命令の断片をつなぎ合わせる攻撃は防げない |
| **ASLR** | プログラム・ライブラリ・ヒープ・スタックの位置を、起動ごとにランダムにする | 書き換え先や飛び先を狙うこと | 範囲外の読み込みなどでアドレスが漏れると破られる（[CWE-122の解説](CWE-122_ヒープベースのバッファオーバーフロー.md) の「読み込みか、書き込みか」） |
| **スタックカナリア**（MSVC の `/GS`、GCC の `-fstack-protector`） | 戻り先の手前に目印の値を置き、関数から戻る前に壊れていないか確かめる | スタックのはみ出しで戻り先を書き換えること | 検知しても、プロセスを止める（DoS）しかない |
| **ガードページ** | スタックの端に、触ると止まるページを置く | スタックの使い切りが、ほかの領域を壊すこと | 止まるだけ（DoS） |
| **制御フローの保護**（Windows の CFG、Intel の CET など） | 関数ポインタや戻り先が、正しい飛び先かを確かめる | 書き換えた関数ポインタ・戻り先への飛び込み | 対応したビルド・CPU・OSが必要 |
| **AddressSanitizer（ASan）** | 区画の前後に触ってはいけない帯を置き、はみ出しや解放後の使用を検知する | ― | 開発・テスト用。遅いので本番では使わない |

## 12. CVEを読むときに見るところ

1. **空間か時間か**: 範囲の外に触るのか、解放後などに触るのか。
2. **読み込みか書き込みか**: 読み込みなら情報漏えい・DoS、書き込みならコード実行まで考える。
3. **攻撃者が決められるもの**: 中身、大きさ、タイミングをどこまで決められるか。
4. **どのプロセスで起きるか**: 実行されたときの権限（Webワーカー、利用者、SYSTEM など）。
5. **届く経路**: その機能や拡張が有効か、外に公開しているか、どんな入力が必要か。
