# ヒープベースのバッファオーバーフロー（CWE-122）

作成日: 2026-10-23

CVEの記録によく出てくる「ヒープベースのバッファオーバーフロー」と、その周辺の用語をまとめる。

---

## ひとことで

**プログラムが実行中に確保したメモリ（ヒープ）で、確保した大きさを超えた場所を読み書きしてしまう欠陥**。C・C++のように、メモリの範囲を自動で確かめない言語で書かれたソフトで起きる。

PHP・JavaScript・Javaのコードそのものでは、まず起きない。起きるのは、それらを動かしている処理系（PHP本体や拡張機能、Node.jsが使うライブラリなど）のC・C++の部分。

---

## 前提: スタックとヒープ

プログラムが使うメモリには、大きく2つの置き場所がある。

| | スタック | ヒープ |
|---|---|---|
| 何を置くか | 関数のローカル変数、引数、関数の戻り先 | 実行してみるまで大きさが決まらないデータ（文字列、配列、オブジェクトなど） |
| 確保と解放 | 関数に入ると確保され、抜けると自動で消える | プログラムが明示的に確保・解放する（Cなら `malloc()`・`free()`） |
| 大きさ | 小さい（OSの既定で1〜8MB程度） | 大きい |
| 寿命 | その関数の中だけ | 解放するまで |

PHPの文字列・配列・オブジェクトは、ヒープに置かれている。

アドレス、仮想メモリ、スタックの中身、整数のあふれなど、土台の話は [メモリの基礎.md](メモリの基礎.md) にまとめてある。

---

## バッファオーバーフローとは

「バッファ」は、データを入れるために確保したメモリの区画。確保した大きさを超えて読み書きすると、**隣にある別のデータ**に触れてしまう。

```text
確保した区画（8バイト）     隣の区画（別のデータ）
[ h e l l o \0 _ _ ][ 別の文字列、オブジェクト、管理情報 ... ]
                    ↑ ここから先に触れるのがオーバーフロー
```

- ヒープ上の区画で起きるもの → **ヒープベース**（CWE-122）
- スタック上の区画で起きるもの → **スタックベース**（CWE-121）

---

## 読み込みか、書き込みか（ここが重要）

「バッファオーバーフロー」という言葉は、人によって指す範囲が違う。MITREのCWE-122のページも、書き込みだけを指す人もいれば、読み込みを含める人もいる、と書いている。CVEの深刻さを判断するときは、**範囲外を「読む」のか「書く」のか**を確かめる。

| | 範囲外の読み込み | 範囲外の書き込み |
|---|---|---|
| CWE | CWE-125（Out-of-bounds Read） | CWE-787（Out-of-bounds Write）。CWE-122 はこの子 |
| 起きること | 隣のデータが漏れる（情報漏えい）。読めない場所に当たって落ちる（DoS） | 隣のデータを書き換える（メモリ破壊） |
| 最悪の場合 | 秘密の値（鍵、パスワード、トークン）や、メモリのアドレスが漏れる。漏れたアドレスは、ASLR（後述）を破る材料になる | **任意のコード実行** |
| 深刻さの目安 | 中程度が多い | 高いことが多い |

### 名前に惑わされない

- メモリの不正なアクセスを見つけるツール AddressSanitizer（ASan）は、範囲外の読み込みも書き込みも「heap-buffer-overflow」と報告する。区別は後ろに付く `READ` か `WRITE` でわかる。
- GitHubのアドバイザリでも、読み込みの問題に CWE-122 が付いていることがある。

記録の中の例:

| CVE | 付いているCWE・タイトル | 実際の中身 |
|---|---|---|
| [CVE-2026-92842](../PHP/2026/09/24/CVE-2026-92842.md) | CWE-122 と CWE-125 | ASanの報告は「READ of size 2」。**読み込み**で、主なリスクは情報漏えい |
| [CVE-2026-91767](../PHP/2026/09/24/CVE-2026-91767.md) | CWE-122。タイトルも「Heap-buffer-overflow」 | `memchr()` が範囲外を**読み続ける**。ヒープの中身は攻撃者に返らず、影響はクラッシュ（DoS） |
| [CVE-2025-14181](../PHP/2026/09/24/CVE-2025-14181.md) | なし | 区画の後ろに**書き込む**。クラッシュからメモリ破壊まで |
| [CVE-2026-111497](../Node.js/2026/10/21/CVE-2026-111497.md) | なし | Brotliの展開で、区画の外に**書き込む**。リモートコード実行の恐れ |

---

## なぜ書き込みはコード実行につながるのか

ここでは考え方だけを扱う。

1. ヒープには、いろいろなデータが隣り合って並んでいる。その中には、**次に呼ぶ関数の場所（関数ポインタ）**や、**空き領域を管理するための情報**も含まれる。
2. 範囲外に書き込めると、それらを攻撃者の決めた値に書き換えられる。
3. 書き換えた関数ポインタが呼ばれると、攻撃者の決めた処理に飛ぶ。

- MITREは、関数ポインタを明示的に使っていないプログラムでも影響を受けるとしている。処理系やC++のオブジェクトの仕組みが、内部で使っているため。
- 攻撃者は、狙ったデータが脆弱な区画のすぐ隣に来るように、事前に確保と解放を繰り返して**メモリの配置を整える**ことが多い（ヒープグルーミングと呼ばれる）。
  - [CVE-2026-109619](../PHP/2026/10/21/CVE-2026-109619.md) の「メモリの配置を細工すると、コード実行につながる」は、このこと。
  - 成功しやすさが「メモリの配置によって変わる」（[CVE-2026-109618](../PHP/2026/10/21/CVE-2026-109618.md)）のも、同じ理由。

## よくある原因（記録に出てきたもの）

### 1. 大きさの計算が桁あふれする（整数オーバーフロー、CWE-190）

```text
確保する大きさ = 長さ + ヘッダーの大きさ   ← 長さが巨大だと、足した結果があふれて小さな値になる
→ 小さな区画しか確保されない
→ 本来の長さぶん書き込んで、区画の外にはみ出す
```

- [CVE-2025-14181](../PHP/2026/09/24/CVE-2025-14181.md): SOAPクライアントが応答を読む処理。あふれを確かめる処理そのものが、符号付き整数のオーバーフロー（Cでは未定義動作）に頼っていたため、コンパイラに消された。
- [CVE-2026-91767](../PHP/2026/09/24/CVE-2026-91767.md): 符号なし整数（`size_t`）の引き算が、マイナスになるはずのところで巨大な値に化けた。
- [CVE-2026-6103](../PHP/2026/09/24/CVE-2026-6103.md)（Phar）も整数の桁あふれ。ただし、こちらはメモリ破壊ではなく、TARを読む位置がずれる問題。

### 2. 確保した大きさと、使う長さが食い違う

- [CVE-2026-92842](../PHP/2026/09/24/CVE-2026-92842.md): NULで止まる関数でコピーしたので区画は短くなったのに、長さは元の値を使い続けた。

### 3. 1つずれる（off-by-one、CWE-193）

- [CVE-2026-93682](../PHP/2026/09/24/CVE-2026-93682.md): 空の文字列の「2文字目」を読んで、区画の1バイト後ろに触れた。

### 4. 受け取ったデータを、残りの長さを確かめずに読む

- [CVE-2025-1218](../PHP/2026/09/24/CVE-2025-1218.md)（mysqlnd）: 「最低1バイト残っている」ことしか確かめずに、2バイト以上読んでいた。

## 近い種類の脆弱性

| CWE | 名前 | 中身 | 記録の例 |
|---|---|---|---|
| CWE-121 | スタックベースのバッファオーバーフロー | スタック上の区画からはみ出す | — |
| CWE-122 | ヒープベースのバッファオーバーフロー | ヒープ上の区画からはみ出す。CWE-787 の子 | [92842](../PHP/2026/09/24/CVE-2026-92842.md)、[91767](../PHP/2026/09/24/CVE-2026-91767.md) |
| CWE-125 | 範囲外の読み込み | 区画の外を読む（ヒープ・スタックを問わない） | [92842](../PHP/2026/09/24/CVE-2026-92842.md)、[93682](../PHP/2026/09/24/CVE-2026-93682.md)、[1218](../PHP/2026/09/24/CVE-2025-1218.md) |
| CWE-787 | 範囲外の書き込み | 区画の外に書く（ヒープ・スタックを問わない） | [14181](../PHP/2026/09/24/CVE-2025-14181.md)、[Node.js 111497](../Node.js/2026/10/21/CVE-2026-111497.md) |
| CWE-416 | 解放後の使用（use-after-free） | 解放済みの区画を使い続ける。その場所には、もう別のデータが入っている | PHP2Shell（[109618](../PHP/2026/10/21/CVE-2026-109618.md)、[109619](../PHP/2026/10/21/CVE-2026-109619.md)） |
| CWE-190 | 整数オーバーフロー | 計算結果があふれて、小さな値や負の値になる。オーバーフローの原因になりやすい | [14181](../PHP/2026/09/24/CVE-2025-14181.md)、[91767](../PHP/2026/09/24/CVE-2026-91767.md)、[6103](../PHP/2026/09/24/CVE-2026-6103.md) |

- 「記録の例」は、アドバイザリに付いたCWEではなく、中身から分類した。
- use-after-free はオーバーフローではないが、「もう自分のものではないヒープの場所に触れる」という点で仲間。PHP2Shellは、これがリクエストをまたいで起きる問題。

## PHPの場合

### Zend メモリマネージャー（ZendMM）

PHPは、確保のたびにOSの `malloc()` を呼ぶのではなく、**独自のメモリ管理（ZendMM）**でヒープを管理している。

- **2MB の塊（chunk）** を **4KB のページ**に分けて使う。
- **3072バイト以下**の小さな確保は、同じ大きさの区画を並べた「ビン」から渡す。大きさは 8、16、24、32…3072バイトの30種類。
  - [CVE-2026-93682](../PHP/2026/09/24/CVE-2026-93682.md) の「1バイトの割り当ては8バイトの区画に入るので、ふつうはクラッシュしない」は、このビンの話。
- ZendMM はリクエストごとに始まり、リクエストが終わると、そのリクエストで確保したメモリを片付ける。
  - ワーカーを使い回すので、片付けが不完全だと、次のリクエストに古い状態が残る。これが [CVE-2026-109619](../PHP/2026/10/21/CVE-2026-109619.md) の土台。
- ZendMM で確保したメモリは、すべて `memory_limit` に数えられる。[CVE-2026-109618](../PHP/2026/10/21/CVE-2026-109618.md) は、この上限に達したときの処理の問題。
- メモリ破壊を見つけると「zend_mm_heap corrupted」と出すことがある。

### `USE_ZEND_ALLOC=0` が出てくる理由

- 環境変数 `USE_ZEND_ALLOC=0` で起動すると、ZendMM を使わず、確保をすべてOSの `malloc()` に回す。
- ASan は、`malloc()` で確保した区画の前後に「触ってはいけない帯」を置いて、はみ出しを検知する。ZendMM の区画は塊の中にすき間なく並んでいるので、そのままでは隣の区画へのはみ出しを検知できない（この理由づけは私の補足。PHP Internals Book は「メモリのデバッグに便利」とだけ書いている）。
- そのため、[CVE-2026-91767](../PHP/2026/09/24/CVE-2026-91767.md) の実証では `USE_ZEND_ALLOC=0` を付けている。

### PHPのアプリを作る側から見ると

- **PHPのコードで、このバグを直接書くことはできない**。PHPの文字列や配列は、範囲を自動で確かめるから（FFI拡張で生のメモリを扱う場合は別）。
- 原因はPHP本体（C）にあり、**直せるのはPHPの更新だけ**。
- アプリ側でできるのは、脆弱な処理に届く入力を減らすこと。これは緩和策で、修正の代わりにはならない。
  - リクエストの大きさを制限する。
  - 使わない機能や拡張を無効にする。例: [CVE-2025-14181](../PHP/2026/09/24/CVE-2025-14181.md) と [CVE-2026-91765](../PHP/2026/09/24/CVE-2026-91765.md) は、soap 拡張を無効にしているこのPCのXAMPPには届かない。

## 防ぐ仕組み・見つける仕組み

### 作る側

- **範囲を確かめる**: 読み書きの前に、残りの大きさを確かめる（[CVE-2025-1218](../PHP/2026/09/24/CVE-2025-1218.md) の修正）。
- **桁あふれしない計算**: 大きさは `size_t` で持ち、足し算・掛け算の前に上限を確かめる。PHPの `zend_string_safe_realloc()` のような、検査付きの関数を使う（[CVE-2025-14181](../PHP/2026/09/24/CVE-2025-14181.md) の修正）。
- **ファジング**: 壊れた入力を大量に自動で作って流し込み、ASan で検知する。
- **メモリ安全な言語**: Rust などは、範囲外のアクセスを言語の仕組みで防ぐ。MITREも、範囲を自動で確かめる言語やコンパイラを、最初の対策に挙げている。

### 動かす環境

- **ASLR**: プログラムやライブラリを置くアドレスを毎回ランダムにする。攻撃者が書き換え先を狙いにくくなる。ただし、範囲外の読み込みでアドレスが漏れると破られる。
- **DEP / NX**: ヒープなどデータ用のメモリにあるものを、命令として実行させない。
- どちらも多層防御の一部で、完全ではない（MITRE）。

### 使う側（自分）

- **更新する**。これが唯一の根本対策。
- 届く経路を減らす。使わない拡張を無効にする、外に公開しない。
